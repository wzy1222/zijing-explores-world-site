本页目录

每周知识生产、视频发布与公开网站更新规范 ​

目标：每周只维护一份带日期的核心正文。正文审核后直接成为当周知识快照，再从同一正文生成图片和视频；VitePress 直接读取本地 Markdown，生成对外 Webpage。避免重复文档和多处改写。

1. 当前判断 ​

现在应该先写规范并手工跑通第一期，暂时不建设飞书镜像、站内评论或复杂内容系统。

原因：第一期尚未验证周正文长度、图片结构、视频时长、网站阅读路径和公开边界。此时直接自动化，会把尚未稳定的流程固化进工具。正确顺序是：

  1. 冻结本规范和文件契约；
  2. 手工完成第一期；
  3. 连续运行 2—3 期，记录重复步骤和错误；
  4. 再补充自动构建与发布，只处理确定、重复且可验证的部分。

2. 本地信息组织 ​

text
personal_thinking/
├── index.md                    # 网站首页与新读者入口
├── .vitepress/                 # 网站导航、主题与构建配置
├── public/                     # 网站公开静态资源
├── docs/
│   ├── personal-development.md
│   └── weekly-knowledge-publishing-workflow.md
├── knowledge/
│   ├── global/                 # 当前认知：原页面持续更新
│   └── weekly/                 # 历史路径：每周一份带发布日期的正文快照
├── publishing/
│   └── YYYY-MM-DD/             # 由当周正文派生的图片、视频和发布记录
└── assets/infographics/        # 跨周复用的全局图与明细图

2.1 全局认知 ​

  • docs/personal-development.md 是个人挑战的总入口；
  • knowledge/global/ 保存以后逐渐增加的主题认知，例如项目选择、商业验证、合作、产品、获客和现金流；
  • 同一主题始终更新原文字和原图，不创建多个“最终版”；
  • 更新时记录本周新增、修正或否定的判断，并链接对应周快照。

2.2 每周快照 ​

  • 位置：knowledge/weekly/YYYY/YYYY-MM-DD.md，日期取该期预计或实际发布日期；
  • 每周只创建一份日期正文；审核冻结后，它本身就是主快照，不再创建内容相同的第二份文档；
  • 发布后不静默改写原判断；确需纠错时追加“后续修正”，并链接修正发生的周；
  • 连续快照必须能够还原真实事件、选择、行动、失败、转向和认知变化。

2.3 公开产物 ​

每周发布目录建议包含：

text
publishing/YYYY-MM-DD/
├── source-ref.md           # 指向 knowledge/weekly 中冻结正文的路径与哈希
├── image-copy.md           # 图片上的文字与结构
├── video-script.md         # 口播、字幕和镜头节奏
├── cover.png               # 总结图片
├── video.mp4               # 最终视频
└── publish-record.md       # 发布时间、平台链接和发布后数据

图片和视频都是从文字派生的表达层。若图片或视频出现了正文没有的信息，应先补充文字，再重新生成媒体。

3. 唯一工作流 ​

第一步：收集输入 ​

输入包括本周对话里的思考、笔记、事实、行动、结果、情感、问题、外部输入和必要材料。此时不急于形成漂亮结论。

第二步：形成带日期的正文草稿 ​

正文是本周唯一的核心文字产物，至少包含：本周进展、事实结果、关键思考、原判断、认知变化、当前结论和下一步。

第三步：提炼认知变化 ​

明确回答：

  • 本周原来怎么想？
  • 哪个事实支持、修正或推翻了原判断？
  • 现在怎么想？
  • 新判断的适用边界是什么？
  • 下周准备验证什么？

第四步：更新全局认知 ​

把已经形成的新理解更新到对应的全局文字和全局图中。全局认知只表达截至当前的最佳理解，不承担保存全部历史版本的职责。

第五步：冻结日期正文为每周快照 ​

在全局认知更新后审核日期正文，冻结后它直接成为当周最终快照。不要再复制一份内容相同的“快照正文”。正文必须保存本周的变化证据和思考路径：

text
本周事实
→ 原判断
→ 触发变化的证据
→ 推理过程
→ 更新后的判断
→ 对全局认知的具体修改
→ 下周验证

因此，“先更新最新认知，再冻结快照”总体方向正确；但这里的快照就是审核后的日期正文，不是在网站发布以后额外生成的文件。前提仍是草稿、证据和更新前判断已经保留。

第六步：派生图片和视频 ​

从冻结正文派生三层表达：

  1. 冻结正文：完整文字和知识快照；
  2. cover.png：只呈现本周最重要的结构化结论；
  3. video-script.md 与 video.mp4：用口播、字幕、高亮和简单运动解释同一份正文。

第七步：生成公开 Webpage 并验证 ​

  • VitePress 直接读取本地 Markdown，不为网站复制第二份正文；
  • “当前认知”更新稳定页面；每周快照生成带日期的稳定页面；
  • 构建后检查首页、推荐阅读路径、正文关键段、图片、视频或发布链接；
  • 只有本地版本、构建结果和公开页面一致，才能标记该期网站更新完成。

第八步：发布和反馈回流 ​

  • 每周发布一次，不固定星期几；
  • 成功、失败、停滞和方向修正都发布；
  • 发布后把链接、评论问题、最多 5 个代表问题和后续行动写回本地；
  • 短期反馈只从抖音、小红书等内容平台回流，不建设站内评论；
  • 新反馈进入下一周草稿，不直接覆盖已经冻结的本周快照。

4. 首期视频路线 ​

4.1 工具判断 ​

当前本机已有的程序化视频路线是 OpenMontage + HyperFrames，而不是 HyperCam。HyperFrames 适合：

  • 竖屏信息图；
  • 大字标题和结构化文字；
  • 对架构图局部放大、高亮和移动；
  • 简单转场；
  • 旁白、背景音乐和字幕组合。

如果“HyperCam”指的是屏幕录制工具，它不适合作为本项目的主要生成引擎；如果指的是 HyperFrames，则可以作为第一期的优先方案。

4.2 第一版视频形态 ​

  • 画幅：9:16 竖屏；
  • 内容：只讲一个本周最关键的认知变化；
  • 画面：概要图开场，随后逐段高亮本周进展、关键思考和下一步；
  • 声音：声音服务于思想表达，不把真人旁白作为真实性的必要条件；第一期允许使用明确非模仿性的中性中文 TTS，后续再根据实际效果决定是否更换本人旁白；
  • 字幕：完整、可校对，并控制在手机安全区域；
  • 动效：只使用缩放、移动、高亮和必要转场，不做与内容无关的炫技；
  • 发布前：分别检查文字、画面、旁白、字幕、最终合成视频和隐私边界。

4.3 正文到视频的转换 ​

text
冻结日期正文
→ 一句话核心结论
→ 3—5 个叙事段落
→ 每段对应一个画面重点
→ 口播与字幕
→ HyperFrames 合成
→ 手机实看与最终检查

第一期不让视频反过来决定知识结构。知识文字先成立，视频只是它的一种阅读方式。

5. 公开网站规范 ​

5.1 系统边界 ​

  • 本地 Markdown 与 Git 历史是唯一真相源；
  • VitePress 是由真相源自动生成的公开阅读层，不是另一套知识库；
  • 短期不使用 GitBook、飞书镜像、数据库或站内评论；
  • 外部读者可以通过内容平台评论提出建议，但不能直接修改正文；
  • 原始证据、客户隐私、合作方保密信息、凭据和未公开内容默认不进入公开网站。

5.2 阅读结构 ​

公开网站先保持三层：

text
开始阅读
├── 当前认知        # 截至今天，我现在怎么看
├── 演化日志        # 每周快照，保留当时判断
└── 事实与证据      # 与公开结论直接相关的可核验材料
  • 新读者优先从“开始阅读”和“当前认知”理解全局；
  • 持续跟进者通过“演化日志”查看每次调整；
  • 当前认知使用稳定 URL 原地更新；每周快照使用带日期的稳定 URL，发布后不静默改写；
  • 图片和视频用于降低理解成本，不能代替完整文字。

5.3 构建与核对 ​

当前只需要四个动作：

  1. 更新并审核本地 Markdown；
  2. 提交 Git，保留可追溯版本；
  3. 构建 VitePress 并检查本地预览；
  4. 发布到 GitHub Pages 后，从外部网络请求和实际浏览器分别核对公开页面、图片、链接和版本是否一致。

只有当评论收集已成为可测量的真实瓶颈时，才增加新的反馈层。建议触发条件满足任意一项后再评估：

  • 连续 3 周整理跨平台反馈均超过 30 分钟；
  • 出现至少 10 名稳定参与者，需要围绕具体段落持续讨论；
  • 出现明确的共同审阅者，需要可追踪的建议与处理状态。

6. 第一期执行边界 ​

本周末第一期建议只完成：

  1. 一份带日期的正文草稿；
  2. 一次全局认知更新；
  3. 审核正文并冻结为第一份周快照；
  4. 一张总结图片；
  5. 一条 HyperFrames 简短视频；
  6. 用 VitePress 生成“当前认知”和第一份“每周快照”页面；
  7. 检查网站阅读路径、正文、图片、视频链接和移动端显示；
  8. 发布前由用户本人最终确认。

完成第一期后，再根据真实摩擦决定自动构建与发布工具写到什么程度。

2026-07-26 修订：旧版“本地单向同步飞书”方案不再是短期工作流。当前采用“本地 Markdown + Git → VitePress Webpage”，评论暂时留在内容平台。
